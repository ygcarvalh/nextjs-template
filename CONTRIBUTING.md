# Contributing

## Setup

```bash
pnpm install
cp .env.example .env.local
pnpm dev
```

Node 22.13+ and pnpm 11. `engines` in `package.json` names both ranges and `.npmrc` sets `engine-strict=true`, so a mismatch stops `pnpm install` with a message instead of failing later in the build. `.nvmrc` picks the major for `nvm use` and the `packageManager` field pins the pnpm release.

## Before you push

```bash
pnpm verify                              # typecheck, lint, coverage, build
pnpm audit --prod --audit-level moderate  # known advisories in what ships
pnpm test:e2e                            # needs the sibling API running
```

`pnpm verify` needs `.env.local`: the build imports `src/env.ts`, which has no default for `API_URL` on purpose. There is no CI workflow, so those three are the whole gate. The hooks run most of it for you: `lint-staged` on commit, `commitlint` on the message, and on push typecheck, the unit suite, and the browser suite when the API answers — it says so and skips when it does not.

`pnpm test:e2e` drives a production build against a live `fastapi-template`. Run `pnpm exec playwright install chromium` once after cloning and again after a `@playwright/test` bump; the browser build is keyed to the package version. Start it with `docker compose up -d` in that repository; the suite registers an account of its own and deactivates it afterwards, or takes `E2E_EMAIL` and `E2E_PASSWORD` if you would rather name one. It fails in one second with a readable message when the API is not answering.

## Commits

Conventional Commits, header only, 50 characters or fewer, imperative mood, no trailing period. Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`. Put the reasoning in the pull request instead of the commit body.

## Layout

Each feature owns its types, server code, components, and tests:

```
src/features/<name>/
  index.ts          # client-safe exports
  types.ts          # zod schemas + inferred types
  server/
    index.ts        # server-only exports and the composition point
    *-repository.ts # the port
    *-service.ts    # use cases, which take the port
  components/
```

Two rules hold this together.

Components must not import a feature's server layer, which Biome enforces through `noRestrictedImports`. Import a Server Action, call a route handler, or take the data as a prop from a Server Component instead. Server Actions live in `server/*-actions.ts` and are the one allowed exception.

Services depend on a port rather than on a concrete store, so swapping the in-memory repository for a database should touch the adapter and one binding and nothing else.

Route handlers under `src/app/api` are HTTP adapters. Authenticate, parse, delegate, map the result to a status code. Rules belong in the service.

A write is a Server Action when its reply is the point, and a route handler when the form only needs to know whether it worked — see [Which one a write should be](README.md#which-one-a-write-should-be).

## Tests

Tests sit next to the code they cover. The extension picks the environment:

- `*.test.ts` runs in node, for server code
- `*.test.tsx` runs in jsdom, for components

The split is load bearing. `@t3-oss/env-nextjs` decides whether server variables are readable by checking for a `window`, so a server module tested under jsdom refuses to hand over `API_URL`.

Coverage thresholds are enforced and sit just under the current numbers. Files excluded from coverage are the ones the Playwright suite covers for real: route entry points, boundaries, and Server Actions.

```bash
pnpm test              # watch-free unit and component tests
pnpm test:watch
pnpm test:coverage
pnpm test:e2e          # builds, starts, and drives a real browser
```

Playwright runs against the production build rather than the dev server, and serially, because the demo repository is one in-process array.

## Styling

Colors, radii, and fonts are tokens in `src/app/globals.css`. Change them there rather than in components. `src/components/ui/**` is generated by the shadcn CLI and is excluded from linting.

One gotcha: when applying `buttonVariants()` to something that is not a `Button`, such as a `Link`, wrap it in `cn()`. Without it the base `border-transparent` and the variant's `border-border` both survive and the border disappears.

```tsx
<Link href="/notes" className={cn(buttonVariants({ variant: "outline" }))}>
```

## Adding a shadcn component

```bash
pnpm dlx shadcn@latest add <component>
```

## Releases

`CHANGELOG.md` is generated from the commit history with [git-cliff](https://git-cliff.org), configured in `cliff.toml`. The binary is not a dependency of this repository; `pnpm dlx` fetches it on demand.

```bash
pnpm dlx git-cliff@2.13.1 --tag v1.0.0 --output CHANGELOG.md
git add CHANGELOG.md package.json
git commit -m "chore: release v1.0.0"
git tag -a v1.0.0 -m v1.0.0
```

Bump `version` in `package.json` first, then regenerate, then tag. Versioning is semver: a change to the template's layout, configuration or the shape of a port is a major bump, a new slice or screen is a minor one, and everything else is a patch. The changelog tracks the template itself: clear it when you start a project from this repository, since the history belongs to the template rather than your app.
